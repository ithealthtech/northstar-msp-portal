Security model

Identity is not authorization.

Microsoft Entra proves who someone is and supplies a coarse application-role ceiling. It does not, by itself, grant access to a single client record.

The authorization chain

Every authenticated request runs all seven steps, in order. A failure at any step denies the request and is audited.

  1. Validate the access tokenSignature, issuer, audience, expiry, tenant, client application, delegated API scope, and a recognized app role.
  2. Resolve the userBy provisioned Entra tenant ID and object ID.
  3. Require an active database identityNo active record, no access.
  4. Resolve scopeAn active client membership or an MSP platform assignment.
  5. Intersect rolesThe Entra app role is intersected with the database role — the narrower of the two wins.
  6. Resolve the targetThe allowed company, or the assigned MSP portfolio.
  7. Enforce the route permissionThe specific named permission that route requires.

Why the company claim is only a hint

The company_id claim in a token is treated as a selection hint, never as a source of access. It cannot create a membership or expand tenant reach.

✓

A client user who guesses another company's resource ID receives a not-found response — not a forbidden response. The portal does not confirm that the other company's record exists.

Provisioned, not just-in-time

Portal users are deliberately not created from an email address or a company claim on first sign-in. The Entra tenant/object pair must already exist in the database.

This is the single most important operational consequence of the model: a valid Entra user in your tenant who has never been provisioned can authenticate and still reach nothing.

i

No default administrator or password is ever created. Complete first-run setup or provision an Entra identity explicitly. See provisioning.

Roles

Entra application roles supply the ceiling:

Entra app rolePurpose
ClientPortal.UserEnd-user self-service
ClientPortal.AdminClient administration
ClientPortal.OwnerClient ownership
MSPPortal.AdminInternal MSP administration
MSPPortal.OwnerInternal MSP ownership

The token must carry the Portal.Access delegated scope and one recognized application role. Database roles are client_user, client_admin, client_owner, msp_operator, msp_admin, and msp_owner.

MSP identities may use PORTAL_PLATFORM_SCOPE=all; otherwise their clients must be explicitly assigned in msp_company_scopes. An MSP administrator does not implicitly see every client.

Demo and preview modes

!

Production startup rejects DEMO_MODE=true. This is enforced at boot, not by convention.

Preview roles are available only under file:// or an explicitly enabled, unconfigured local demo. Once Entra is configured, preview buttons and saved preview roles are ignored entirely.

When the portal is served from 127.0.0.1 with local demo mode on, the role buttons use local-only demo identities that resolve through the same session, repository, SQLite, permission, and audit pipeline as real Entra users — so the demo exercises the real authorization path rather than bypassing it. The demo authorization header is rejected for non-loopback callers and is fully disabled when demo mode is off.

API response discipline

  • Unknown API paths return JSON 404 responses.
  • Unsupported methods return 405 with an Allow header.
  • Responses include a request ID, security headers, and no-store caching.
  • Denials are durably audited, tenant-aware, and return generic errors.

New routes are required to default to denied access, enforce the narrowest permission, validate bounded input, return generic errors, and ship with tenant-isolation tests.

Known boundary

The included Node SQLite store makes the foundation immediately runnable and enables deterministic isolation tests. It suits local development and a single-node pilot.

Before a multi-instance production rollout: migrate the same repository contracts to PostgreSQL, add tenant-qualified foreign keys and forced row-level security, run the application under a non-owner database role, and test RLS using the real deployment role.

See SECURITY-ARCHITECTURE.md for trust boundaries and deployment requirements, and the security policy to report a vulnerability.
